# 沟通渠道卡片集（lite）

## 使用场景

老人给新人介绍公司有哪些沟通渠道、每个沟通渠道做什么用、如何区分不同用途——这是这份 lite 要解决的第一件事。新人入职时渠道散在各处，没有统一说法，全靠介绍的人凭记忆讲，听的人记不住。

## 由此定下的形态

所以做了一个沟通渠道卡片集，把这些信息卡片化地呈现：一个渠道一张卡，扫一遍就知道有哪些渠道、各做什么用、出问题找谁。

## 卡片字段

- 名称（label）：渠道或群的名字，卡片的标题。
- 用途描述（description）：这个渠道做什么用、什么内容该往这里放。
- 责任人与成员：群主、管理员与成员，谁对这个渠道负责。
- 关系与分类：群与群之间的关系——正式群与闲聊群的分界，职能群、业务群等类别。

## 渠道与平台解耦

渠道名带平台前缀（微信成员群、企业微信成员群、飞书成员群、小红书成员群等），有的平台有 API、有的没有。先假设所有渠道都手动管理，等能自动化时再通过适配层把它们接上，卡片本身不与具体平台绑定。

## 原始想法

沟通管理需要记录群聊的功能。像我们的群聊分的比较细，哪些该讲什么就是重难点。要把沟通渠道管理到位。

它应该是一个比如说卡片形式的去展示我手上的群的资产，或者是叫 label 群的名称，然后呃 description 对这个群的功能的描述然后呃群成员、群主这些就责任人啊、成员呀这些，然后呃群之间的关系，就比如说我们有一些正式群和闲聊群，这个里面就存在了一个关系的分界啊等等，还有一些呃专门的职能群啊、业务群啊等等，就是说我们本身会对它有一个还会有个类别的分类。

对，然后另外一个比较关键的事情是呃，就是他不需要和具体的那个呃平台进行深度绑定，就比如说我们会叫呃微信成员群、企业微信成员群、飞书成员群、小红书成员群等等。然后呢他们有一些是支持 API 的，有一些不支持，那我们就先假设所有的渠道都先要手动管理，然后未来能够自动化的时候，我们再逐渐地通过适配层把它装上去。
